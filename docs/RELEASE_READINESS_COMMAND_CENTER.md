# ArtistOS release readiness command center

## Purpose

ArtistOS now has one evidence-producing readiness system instead of a collection of informal deployment steps.

The command center does not deploy, mutate production, repair migration history, or grant production approval. It evaluates whether the required evidence exists and produces a deterministic `GO`, `BLOCKED`, or `NO_GO` decision.

## Commands

### Static readiness

```bash
npm run readiness
```

Runs:

1. reviewed migration manifest verification
2. architecture and safety tests
3. TypeScript validation
4. production build
5. optional authenticated E2E environment validation
6. consolidated readiness report generation

This mode is appropriate for GitHub-hosted runners and ordinary pull-request development.

### Full local readiness

```bash
npm run readiness:full-local
```

Runs the static gates plus:

1. historical migration recovery
2. historical clean replay
3. workspace isolation assertions
4. database advisors
5. linked historical schema drift verification
6. pending migration two-stage rehearsal
7. pending schema and RLS assertions

Requirements:

- authenticated Supabase CLI or an approved read-only database URL
- Docker
- sufficient local resources for Supabase
- an isolated execution environment

The command remains local-only for replay and does not call `supabase db push`.

### Strict final-evidence validation

```bash
npm run readiness:validate-evidence
```

This validator rejects superficial pass files. It requires completed authenticated journeys, exact Brain count reconciliation, zero duplicate rows, zero confidence promotion, and production approval bound to the exact commit and migration-manifest digest.

## Decision model

### `GO`

All required evidence artifacts exist and each reports success.

A `GO` report still does not authorize production mutation. A separately reviewed approval artifact and rollout procedure remain required.

### `BLOCKED`

One or more required gates have not yet been executed or their evidence artifacts are absent.

This is the expected state before authenticated recovery and E2E testing.

### `NO_GO`

A gate executed and produced failing or malformed evidence.

Production work stops until the failure is understood and corrected.

## Required evidence contracts

### Historical recovery

Expected evidence:

```text
artifacts/schema-drift/summary.txt
```

The file must contain the successful no-drift marker generated by the historical recovery workflow.

### Pending rehearsal

Expected evidence:

```text
artifacts/pending-migration-rehearsal/summary.txt
```

The file must contain `RESULT: PASS`.

### Authenticated E2E

Expected evidence:

```json
{
  "status": "pass",
  "summary": "All authenticated journeys and isolation checks passed.",
  "run_id": "...",
  "base_url": "...",
  "completed_at": "...",
  "journeys": [
    { "id": "owner-release-workflow", "status": "pass" },
    { "id": "cross-workspace-denial", "status": "pass" }
  ]
}
```

Stored at:

```text
artifacts/authenticated-e2e/summary.json
```

### Brain reconciliation

Expected evidence:

```json
{
  "status": "pass",
  "summary": "Brain v1 and v2 reconciled with no unexplained rows.",
  "source_rows": 0,
  "mapped_rows": 0,
  "exception_rows": 0,
  "duplicate_rows": 0,
  "confidence_promotions": 0,
  "completed_at": "..."
}
```

Stored at:

```text
artifacts/brain-reconciliation/summary.json
```

`source_rows` may be zero only when Brain v1 is genuinely empty. Every source row must be mapped or included in an explicit exception report. Confidence promotions and duplicate rows must always equal zero.

### Production approval

Expected evidence:

```json
{
  "status": "pass",
  "summary": "Production rollout approved for the identified commit and migration set.",
  "git_sha": "...",
  "migration_manifest_sha256": "...",
  "approved_by": "...",
  "approved_at": "...",
  "rollback_owner": "..."
}
```

Stored at:

```text
artifacts/production-rollout/approval.json
```

This artifact is commit-specific and must never be reused after the branch head or migration set changes.

## Output

The report generator writes:

```text
artifacts/release-readiness/report.json
artifacts/release-readiness/report.md
artifacts/release-readiness/events.ndjson
```

Evidence files receive SHA-256 digests in the report so review can confirm that the evaluated artifacts did not change.

## GitHub Actions

The manual `ArtistOS Release Readiness` workflow supports:

- `static`: GitHub-hosted source and build verification
- `full-local`: protected self-hosted recovery and database rehearsal

The full-local job requires the `artistos-release` runner label and the `artistos-release-rehearsal` GitHub environment. This keeps database credentials and Docker-based recovery out of ordinary pull-request runners.

## Non-negotiable safety rules

- Never use migration repair to make the ledger appear reconciled.
- Never run linked or URL-based database reset.
- Never use the readiness command to apply production migrations.
- Never interpret a report as deployment authorization.
- Never delete Brain v1 during recovery or rehearsal.
- Never accept a readiness artifact whose commit does not match the reviewed release commit.
